# Android 功能交付流程

收到功能需求后，严格按以下四个阶段执行。**禁止跳过 Phase 1-2 直接编码。**

## Phase 1: 需求拆解

用以下结构梳理需求，将模糊的描述转化为明确的待办：

```
## 需求理解
- 一句话目标：[用户要什么]
- 涉及的用户场景：[谁、在什么情况下、做什么操作]

## 功能拆解
- [ ] 子功能 1：...
- [ ] 子功能 2：...

## 边界与约束
- 需要支持的 Android 版本范围：
- 需要适配的屏幕/设备类型：
- 性能要求（如响应时间、内存）：
- 与现有功能的交互：
```

## Phase 2: 不确定点确认

将分析中发现的所有不确定点，分类汇总后一次性与用户确认。

**确认模板：**

```
我对需求的理解如下：
✅ 明确的部分：
1. ...
2. ...

❓ 需要确认的部分：
1. [问题] — 我倾向于 [方案A]，因为 [理由]。还是你希望 [方案B]？
2. [问题] — 有两种做法：
   - A: [描述] → 优点：... / 缺点：...
   - B: [描述] → 优点：... / 缺点：...
   建议选 [X]，原因是 ...
```

**关键原则：**
- 每个问题附带倾向性建议，不做纯甩锅式提问
- 用 AskQuestion 工具（如可用）提供结构化选项，降低用户决策成本
- 一次性收集所有问题，避免多轮碎片化确认
- 如果没有不确定点，明确告知用户"需求清晰，以下是方案"，直接进入 Phase 3

## Phase 3: 技术方案

确认完成后，输出实现方案：

```
## 技术方案

### 架构层面
- 采用的架构模式：[MVVM/MVI/...]
- 新增/修改的模块：

### 实现计划
| 步骤 | 文件 | 改动说明 | 风险点 |
|------|------|----------|--------|
| 1 | | | |
| 2 | | | |

### 关键设计决策
- [决策1]：选择 X 而非 Y，因为 ...
```

对于简单需求（如修改一个按钮文案），Phase 3 可简化为一句话说明。

## Phase 4: 编码实现

按 Phase 3 的计划逐步执行：

1. 使用 TodoWrite 创建任务清单，跟踪进度
2. 每完成一个步骤，检查 lint 错误
3. 改动完成后，向用户简要汇报：改了什么、为什么这样改

## 流程选择指南

并非所有需求都需要完整四阶段。根据复杂度选择：

| 需求类型 | 流程 | 示例 |
|----------|------|------|
| 琐碎改动 | 直接 Phase 4 | 改文案、调颜色、加日志 |
| 小功能 | Phase 1 → 4 | 加一个按钮点击事件 |
| 中等功能 | Phase 1 → 2 → 4 | 新增一个列表页、接入一个 API |
| 复杂功能 | Phase 1 → 2 → 3 → 4 | 新模块、架构变更、跨模块功能 |

判断标准：**如果你对"该怎么做"有任何犹豫，就走完整流程。**
