# 通用编码规范

适用于所有编程语言和项目的通用编码原则。

## 设计原则

### SOLID 原则

- **S (单一职责)**: 每个模块/类/函数只做一件事，并且只有一个原因去修改它。
- **O (开闭原则)**: 对扩展开放，对修改关闭。通过抽象和多态扩展功能，而非修改已有代码。
- **L (里氏替换)**: 子类应能完全替代父类，不破坏程序正确性。
- **I (接口隔离)**: 接口应小而专一，不应强迫客户端依赖它不使用的方法。
- **D (依赖倒置)**: 高层模块不应依赖低层模块，两者都应依赖抽象。

### 其他核心原则

- **DRY (Don't Repeat Yourself)**: 消除重复代码。同一逻辑只应出现在一处。
- **KISS (Keep It Simple, Stupid)**: 优先选择最简单的实现方案。避免不必要的复杂性。
- **YAGNI (You Ain't Gonna Need It)**: 不为当前不需要的功能编写代码。需求未明确时不做过度设计。
- **最小惊讶原则**: 代码行为应符合阅读者的直觉预期。

## 命名规范

- **意图明确**: 名称应直接表达其用途，而非描述其实现方式。
- **一致拼写**: 同一概念在全项目使用同一词汇（如 `fetch` vs `get` vs `retrieve`，选一个并坚持）。
- **可读性优先**: `userList` 优于 `ul`，`calculateTotalPrice` 优于 `calc`。
- **避免误导**: 不使用与实际含义不符的名称（如 `AccountList` 不是 List 时）。
- **布尔值**: 使用 `is`/`has`/`can`/`should` 前缀（如 `isActive`, `hasPermission`）。

## 函数/方法设计

- **短小精悍**: 单个函数不超过 30-50 行。超过时考虑拆分。
- **单一抽象层级**: 一个函数内的操作应处于同一抽象层级。
- **参数数量**: 不超过 3-4 个参数。超过时考虑封装为参数对象。
- **无副作用**: 尽量编写纯函数。有副作用时在函数名中体现（如 `saveUser`, `sendNotification`）。
- **早返回**: 使用 early return 减少嵌套层级。

## 注释规范

- **解释「为什么」而非「是什么」**: 代码本身说明了做了什么，注释应解释为什么这样做。
- **不要注释过期的代码**: 直接删除，版本控制系统会保留历史。
- **TODO/FIXME/HACK**: 使用标准化标记并附带负责人和日期：
  ```
  // TODO(zhangsan): 2025-06-01 前替换为异步实现
  // FIXME: 在高并发场景下存在竞态条件
  // HACK: 临时解决第三方库的 bug，v2.1 发布后移除
  ```
- **公共 API 必须注释**: 所有公开接口、类、方法需有清晰文档。

## 错误处理

- **不要吞没异常**: 捕获异常时必须处理或重新抛出，禁止空的 catch 块。
- **使用自定义异常**: 区分业务异常和系统异常，提供有意义的错误信息。
- **尽快暴露，尽量延迟处理**: 在下层尽早发现错误并抛出，在上层统一处理和记录。
- **错误信息要有上下文**: 包含操作名称、关键参数值、失败原因。

## 测试原则

- **测试金字塔**: 大量单元测试 + 适量集成测试 + 少量端到端测试。
- **FIRST 原则**: Fast（快速）、Independent（独立）、Repeatable（可重复）、Self-validating（自验证）、Timely（及时）。
- **一个测试一个概念**: 每个测试用例只验证一个行为。
- **AAA 模式**: Arrange（准备）→ Act（执行）→ Assert（断言）。
- **命名规范**: `方法名_场景_预期行为`（如 `findUser_WhenUserNotExists_ThrowsException`）。

## 代码审查要点

- 逻辑是否正确且完整
- 边界条件和异常情况是否处理
- 是否存在安全漏洞
- 是否存在性能问题
- 命名是否准确易懂
- 是否有必要的测试
- 是否符合项目既定规范
