# 代码审查规范

统一的代码审查流程和检查清单，适用于所有项目。

## 审查目标

代码审查的核心目标：
1. **发现缺陷**: 在合并前发现逻辑错误和潜在 bug
2. **知识分享**: 让团队成员了解代码变更
3. **一致性保证**: 确保代码符合项目规范
4. **共同所有权**: 建立代码的集体责任感

## 审查流程

### 提交者职责

1. 自审一遍代码，确认无明显问题
2. 确保 CI 流水线通过（构建、测试、lint）
3. 编写清晰的 PR 描述（见 `git-conventions.md` 模板）
4. 保持 PR 体积小（建议不超过 400 行变更）
5. 及时回应审查意见

### 审查者职责

1. 在 1 个工作日内开始审查
2. 区分「必须修改」和「建议优化」
3. 对事不对人，客观描述问题
4. 提供具体的修改建议，而非笼统评价
5. 确认修改后及时批准

## 审查检查清单

### 设计与架构

- [ ] 变更是否必要？能否用更简单的方式实现？
- [ ] 代码结构是否合理？是否放在了正确的模块/包中？
- [ ] 是否引入了不必要的依赖？
- [ ] 是否遵循了项目的架构模式？

### 功能与逻辑

- [ ] 逻辑是否正确？是否遗漏了边界情况？
- [ ] 空值/null 是否处理？
- [ ] 并发场景是否有竞态条件？
- [ ] 异常/错误是否正确处理和传播？
- [ ] 是否考虑了性能和资源消耗？

### 安全性

- [ ] 是否存在注入风险（SQL、命令、模板注入）？
- [ ] 敏感信息是否加密或脱敏？
- [ ] 权限检查是否完整？
- [ ] 输入验证是否充分？

### 测试

- [ ] 是否有足够的测试覆盖？
- [ ] 测试用例是否覆盖了正常流程和异常流程？
- [ ] 测试是否独立可重复？
- [ ] CI 是否全部通过？

### 可维护性

- [ ] 命名是否清晰易懂？
- [ ] 是否有必要的注释（尤其是「为什么」）？
- [ ] 是否有难以理解的复杂逻辑需要重构？
- [ ] 是否有重复代码可以抽取？

### 文档

- [ ] 公开 API 是否有文档？
- [ ] README 或相关文档是否需要更新？
- [ ] 是否有 Breaking Change 未标注？

## 审查意见分类

| 优先级 | 标记 | 含义 |
|--------|------|------|
| 🔴 阻塞 | `[blocking]` | 必须修改才能合并。涉及安全性、正确性、数据丢失。 |
| 🟡 建议 | `[suggestion]` | 建议修改但非强制。涉及可读性、可维护性、轻微性能改进。 |
| 🟢 赞赏 | `[praise]` | 代码写得好的地方，值得学习和推广。 |
| 💬 提问 | `[question]` | 不确定的地方，请求澄清。 |

## 审查示例

### 好的审查意见

```markdown
[suggestion] 这里可以考虑用 `?.let {}` 替代 `if (x != null) { }` 以保持 Kotlin 风格。

[question] 这个超时时间设为 5 秒的依据是什么？上游 API 的 p99 延迟是多少？

[praise] 这个错误处理覆盖得很全面，边界情况都考虑到了 👍
```

### 不好的审查意见

```markdown
这里写得不好。 （缺少具体说明）
改一下。 （缺少修改方向）
我觉得 A 方案更好。 （缺少理由和对比）
```

## 审查时机

- **小改动 (<100 行)**: 随时审查，快速通过
- **中等改动 (100-400 行)**: 安排专门时间审查
- **大改动 (>400 行)**: 建议拆分为多个 PR；或在设计阶段预先讨论方案
